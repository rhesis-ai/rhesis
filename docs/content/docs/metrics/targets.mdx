# Metric Targets

A metric's **target** says what it judges in a test's trace: each turn, the whole conversation, the whole run, each span of one kind, such as every tool call or every retrieval, or each span that meets conditions you write. The target also decides which tests the metric runs on.

## Choices

| `on` | Label | Judges | The metric reads |
| --- | --- | --- | --- |
| `turn` | Each turn | Each turn: the test's one response, or every turn of a conversation on its own | the turn's input and output, and the turn's trace |
| `conversation` | The conversation | The whole conversation, once | the conversation's trace |
| `run` | The whole run | The whole trace, once | the trace |
| `tool_call` | Each tool call | Each tool call | the arguments as input, the result as output, and the call's trace |
| `retrieval` | Each retrieval | Each retrieval | the query as input, the documents found as output, and the retrieval's trace |
| `model_call` | Each model call | Each model call | the prompt as input, the completion as output, and the call's trace |
| `agent` | Each agent | Each agent run | the task as input, the final answer as output, and the agent's trace |
| `guardrail` | Each guardrail check | Each guardrail check | what it checked as input, its decision as output, and the check's trace |
| `span` | Custom spans | Each span that meets its conditions | the span's input and output as its kind reads them, unless `read` names others, and the span's trace |

Each thing a target picks is judged as a trace of its own: the span and everything under it. A metric that reads the trace gets that, not the whole test's trace. On an agent, it holds the agent's own model and tool calls; on a turn, that turn's spans.

A span or a turn is held to the test's goal, instructions and restrictions. A span is not held to the test's expected response or expected tool calls, which describe the whole response. A turn is held to its own expected tool calls: its entry in `expected_tool_calls_per_turn` on a multi-turn test, or the test's `expected_tool_calls` on a single-turn test. So a metric that needs a reference answer can't take a per-span target, and the [Tool Call Trajectory](/docs/metrics/tool-calls) metric takes `turn`, `conversation` or `run`.

Otherwise a metric can take the targets that fit what it reads. A judge reads input and output, so it can judge turns and any kind of span. A [code metric](/docs/metrics/code-metrics) that declares `trace` can take every target. A conversational metric judges the conversation. A target the metric can't take is refused when it is saved, with the choices it can take. Each metric the API returns lists its `supported_targets`. `GET /metrics/targets` returns `targets`, every choice with its label and `span_kind`. It also returns what a span target is built from: `operators` and `special_fields` for its conditions, and `readers` and `event_prefix` for its `read` (see [Span targets](#span-targets)). A core install, which runs no metrics, gets empty lists and a `null` `event_prefix`.

The per-span presets take two refinements. `name` keeps only spans with this tool, agent or model name, such as `"issue_refund"`. `within` keeps only spans inside the agent with this name, at any depth.

The per-span presets and `turn` also take `where`, the [conditions](#conditions) the span must meet. A short form maps attribute keys to values, and a list of values means any of them. For example, only the turns of email conversations, from a REST endpoint whose response mapping maps `metadata.channel`:

<CodeBlock filename="where.json" language="json">
{`{"target": {"on": "turn", "where": {"rhesis.reported.metadata.channel": "email"}}}`}
</CodeBlock>

The short form is stored as conditions with `==` (or `in` for a list), so the API always returns the list form. When `where` leaves nothing to judge, the metric is not applicable, and the reason names the conditions.

## Span targets

A span target, `on: "span"`, judges each span that meets its conditions. Use it when the spans you mean cross kinds, or when no kind fits them. A preset also takes `where`, so a condition on an attribute, the duration or the status alone doesn't need a span target.

<CodeBlock filename="span-target.json" language="json">
{`{
  "on": "span",
  "where": [
    {"field": "kind", "op": "==", "value": "tool.invoke"},
    {"field": "ai.tool.name", "op": "in", "value": ["issue_refund", "cancel_order"]},
    {"field": "status", "op": "==", "value": "ok"}
  ],
  "within": "billing_agent",
  "aggregate": "share",
  "min_share": 0.9
}`}
</CodeBlock>

A span target needs at least one condition; to judge the whole trace, use `run`. It doesn't take `name`. Write a condition on `name` instead. `within`, `read`, `aggregate` and `min_share` work as on the presets.

### Conditions

`where` is a list of conditions, and a span must meet all of them. There is no "or" across conditions; use `in` for a field that may take one of several values. Each condition has a `field`, an `op` and, for most operators, a `value`.

`field` is one of these special fields, or else any span attribute key, read exactly:

| Field | Reads |
| --- | --- |
| `kind` | The span kind, such as `tool.invoke`, `retrieval`, `llm.invoke`, `agent.invoke`, `guardrail` or `endpoint.invoke`. A preset's name works too, and `tool_call` is stored as `tool.invoke` |
| `name` | The tool, agent or model name, else the span name, as a preset's `name` reads it |
| `span_name` | The span's own name |
| `duration_ms` | How long the span took |
| `status` | `ok` or `error`, compared without case |

To read an attribute whose key is also a special field's name, write `attributes.` in front, such as `attributes.status`.

| `op` | `value` |
| --- | --- |
| `==`, `!=` | Text, a number or true/false |
| `<`, `<=`, `>`, `>=` | A number |
| `in`, `not_in` | A list of at least one value |
| `contains` | Text |
| `matches` | A regular expression of at most 1000 characters (see [Regular expressions](#regular-expressions)) |
| `exists`, `not_exists` | None |

Numbers and text compare as the same value, so `200` matches `"200"`. A numeric comparison with a value that isn't a number doesn't match. An unknown operator, or a value of the wrong type for its operator, is refused with the valid choices.

A span that doesn't have the field passes only `!=`, `not_in` and `not_exists`, and fails every other condition on it. So "`app.customer_tier` is not `gold`" keeps spans that carry no tier at all. A span the endpoint reported, rather than traced, has no `duration_ms` or `status`, and counts as missing both.

### Inside an agent

`within` keeps the spans that run inside the agent with this name, at any depth below it. The agent's name is read as the `name` field reads it. A preset's `within` and a span target's `within` mean the same.

### What the metric reads

`read` says what each unit hands the metric as its `input` and `output`. Without it, the metric gets the span kind's own, such as a tool call's arguments and result, or a retrieval's query and documents. Each side takes one of these values.

- An attribute key, such as `ai.tool.arguments`.
- `input` or `output`, the span's own input or output.
- `conversation.input` or `conversation.output`, the turn the unit belongs to. It reads the turn's root span, its `rhesis.conversation.input` or `rhesis.conversation.output` attribute, else the root span's own input or output. So a tool call can be judged against what the user asked in that turn.
- `event:` and an event name, such as `event:ai.retrieval.query`. It reads that event's attribute, or all its attributes when it has several.

A side left out keeps the kind's own. `read` works on targets with several units: `turn`, the per-span presets and `span`. It is refused on `conversation` and `run`.

<CodeBlock filename="read.json" language="json">
{`{"on": "retrieval", "read": {"input": "event:ai.retrieval.query"}}`}
</CodeBlock>

### Presets are short forms

Each per-span preset is a short form of a span target. `{"on": "tool_call", "name": "issue_refund", "within": "billing_agent"}` means:

<CodeBlock filename="expanded.json" language="json">
{`{
  "on": "span",
  "where": [
    {"field": "kind", "op": "==", "value": "tool.invoke"},
    {"field": "name", "op": "==", "value": "issue_refund"}
  ],
  "within": "billing_agent"
}`}
</CodeBlock>

Matching always uses this expanded form, so a preset and the span target it stands for pick the same spans. The SDK's `Target.expand()` gives it. `turn`, `conversation` and `run` are not spans and don't expand. When a preset picks the right spans, keep the preset. It is shorter and reads better in the app.

### Summary text

Each metric the API returns carries `target_summary`, its target in words, and `target_summary_short`. The target above reads "each tool call named `issue_refund` inside `billing_agent`". Kind and name conditions become the noun and "named …". Other conditions follow "where", joined with "and". The short form shows only the first of those and counts the rest, as in "…, where `status` is `ok`, and 1 more condition". The SDK's `Target.describe()` writes both, so the app, the API and the SDK say the same thing.

### Regular expressions

The platform matches `matches` patterns in two places: in Python when it evaluates, and in the database when it lists the spans a target picks. So `matches`, in targets and in `FieldRule` alike, accepts only patterns that mean the same in both, and that can't take exponential time. A pattern that uses one of these is refused when it is saved, with the portable form where there is one.

| Refused | Write instead |
| --- | --- |
| `\d`, `\D` | `[0-9]`, `[^0-9]` |
| `\w`, `\W` | `[A-Za-z0-9_]`, `[^A-Za-z0-9_]` |
| `\s`, `\S` | `[ \t\n\r\f\v]`, `[^ \t\n\r\f\v]` |
| `\b` (word boundary) | `(^\|[^A-Za-z0-9_])` before the word, `([^A-Za-z0-9_]\|$)` after it |
| `\A`, `\Z`, `\z` | `^`, `$` |
| A named group, `(?P<name>...)` or `(?<name>...)` | A plain group, `(...)` |
| An atomic group, `(?>...)` | A plain group, `(...)` |
| Inline flags, such as `(?i)` | Both cases, such as `[Rr]efund` |
| A possessive quantifier, such as `a++` or `a{2}+` | A plain quantifier, such as `a+` or `a{2}` |
| A quantifier with no lower bound, such as `a{,3}` | `a{0,3}` |
| A repeat count over 255, such as `a{300}` | A count of at most 255 |
| A POSIX class `[[:alpha:]]`, a collating element `[[.a.]]` or an equivalence class `[[=e=]]` | The characters themselves, such as `[A-Za-z]`, `a` or `[eé]` |
| `\N{...}`, a character by name | The character itself |
| `\x` with two hex digits followed by another hex digit, such as `\x41B` | The character itself |
| A repeated group whose body repeats something, such as `(a+)+`, or whose alternatives can start with the same character, such as `(a\|ab)*` | A pattern without the nested repeat |
| `\B`, `\G`, a named backreference `(?P=name)`, a lookbehind `(?<=...)` or `(?<!...)`, a comment `(?#...)`, a conditional group `(?(1)...)` | No portable form; rewrite the pattern without it |

`\d`, `\w` and `\s` are refused inside a character class too, since which characters they cover differs between Python and Postgres. A nested repeat is refused because Python's matcher can take exponential time on text that almost matches. The check reads the pattern, not the text, so it also refuses some patterns that are safe, such as `([a-z]+\.)*com`. Patterns such as `(ab)+` and `(cat|dog)+` are kept.

A rule saved before these checks still loads and runs with Python's meaning. It is refused the next time it is saved, until its pattern is rewritten.

### Examples

Each refund issued or order cancelled inside `billing_agent` that went through, with 90% of them required to pass. Failed calls changed nothing, so they are left out:

<CodeBlock filename="refund-policy.json" language="json">
{`{
  "on": "span",
  "where": [
    {"field": "kind", "op": "==", "value": "tool.invoke"},
    {"field": "name", "op": "in", "value": ["issue_refund", "cancel_order"]},
    {"field": "status", "op": "==", "value": "ok"}
  ],
  "within": "billing_agent",
  "aggregate": "share",
  "min_share": 0.9
}`}
</CodeBlock>

It reads "each tool call named `issue_refund` or `cancel_order` inside `billing_agent`, where `status` is `ok`". Conditions read the span's own attributes and fields. A reported span has no status, so a reported tool call is left out here.

Each span of a gold-tier customer, whatever its kind, where the application sets `app.customer_tier` on its spans:

<CodeBlock filename="gold-tier.json" language="json">
{`{"on": "span", "where": [{"field": "app.customer_tier", "op": "==", "value": "gold"}]}`}
</CodeBlock>

It reads "each span where `app.customer_tier` is `gold`". To judge only one kind of span for those customers, add a `kind` condition.

### Finding keys and checking a target

Three endpoints help you write a span target that matches what your endpoint sends.

- `GET /telemetry/attributes` lists the attribute keys each span kind carries.
- `POST /metrics/targets/preview` tries a target on the project's latest traces.
- `GET /telemetry/spans` with `target` lists exactly the spans a target picks.

`GET /telemetry/attributes?project_id=…&kind=tool.invoke&days=7` reads the newest spans of each kind, at most 2000 per kind, from the last `days` (1 to 90, default 7). `kind` narrows it to one kind, and `limit` (default 100, at most 500) caps the keys per kind. For each key it returns the share of spans that carry it (`coverage`), its JSON `type`, its 10 most common values with their counts (`top_values`, long values cut) and its number of `distinct` values. A key where nearly every span has its own value, such as an id, is marked `unique: true`; it makes a poor condition.

<CodeBlock filename="attributes.json" language="json">
{`{
  "kinds": {
    "tool.invoke": {
      "spans": 412,
      "attributes": [
        {"key": "ai.tool.name", "coverage": 1.0, "type": "string", "distinct": 7, "unique": false,
         "top_values": [{"value": "issue_refund", "count": 120, "truncated": false}]}
      ]
    }
  },
  "sampled_spans": 412,
  "since": "…"
}`}
</CodeBlock>

`POST /metrics/targets/preview` takes `{"project_id": …, "target": …, "traces": 50}`. `target` is a target as `config.target` holds it, or a preset's name. It reads the project's latest `traces` traces (default 50, at most 200) and matches the target as evaluation does. It returns how many traces it read (`traces`), how many the target applies to (`matching_traces`) and doesn't (`not_applicable_traces`), how many units a metric would run on (`units`), up to 5 `samples` with each unit's name, input, output, duration and status, and the target's `target_summary`. On a large project it stops matching after a few seconds and returns `partial: true`, with `traces` counting only the traces it read; the app says so under the counts. It changes nothing, so it needs only read access to traces.

`GET /telemetry/spans` takes `target`, a target as URL-encoded JSON, and returns exactly the spans it picks, matched as evaluation matches them. For a span target or a preset, that is each matching span; for `turn`, each turn's root span; for `run`, each trace's first root span; for `conversation`, the first root span of each conversation. It applies together with every other filter. A target that isn't JSON or isn't valid gets a 422 naming the problem. The spans facets take `target` too.

Creating or updating a metric also checks the attribute keys in its `where` against the spans of the last 7 days. A key no recent span carries doesn't stop the save, since the endpoint may not have sent traces yet. The response's `warnings` names it and the nearest key that is carried, such as "No recent span carries app.tier; app.customer_tier is set on 92% of tool.invoke spans".

## Default target

The target is optional. A metric created without one gets its default, which is stored and returned like any other target:

| Metric | Default |
| --- | --- |
| Judges, and other metrics that read input and output | `turn` |
| Conversational Judge, Goal Achievement, and the DeepEval conversational metrics | `conversation` |
| Tool Call Trajectory, and code metrics that read only `trace` | `run` |

## Which tests a metric runs on

- A `conversation` target runs only on multi-turn tests. It never runs on single-turn tests.
- Every other target runs on single-turn and multi-turn tests alike.
- On a multi-turn test, `turn` judges every turn of the conversation on its own. The metric fails when a turn fails, and the result reads "2 of 3 turns passed".
- A metric that needs a reference answer (`ground_truth_required`) is left out of multi-turn tests, since a conversation has no reference answer. For the same reason it can't take the `conversation` target.

So every requirement on a Single-Turn test set needs at least one linked metric whose target isn't `conversation`, or its tests have nothing to judge them.

On live traces, the target decides when the metric runs. See [Trace Metrics](/docs/metrics/trace-metrics).

## Combining the verdicts

A per-span target runs the metric once per matching span, then combines the verdicts with `aggregate`:

| `aggregate` | Passes when | Score |
| --- | --- | --- |
| `all` (default) | every span passes | the first failing span's, else the first span's |
| `any` | at least one span passes | the first passing span's, else the first span's |
| `share` | at least `min_share` (0 to 1) of the spans pass | the share that passed |

The result reads "2 of 3 tool calls passed" and, when the metric fails, names the first span that failed, with its reason. Each span's score and verdict are listed under `spans`. A span the metric gave no verdict is left out of the count; when no span has one, the result is inconclusive. At most 25 spans are judged per metric; the result says when there were more. Turns on a conversation combine the same way.

## When nothing matches

When the trace has no span the target names, the metric is **not applicable** to that test. The result says why ("No tool calls named `issue_refund` were recorded.") and what would report them. It doesn't count towards the test's verdict. A test whose metrics are all not applicable is Inconclusive.

What an endpoint reports decides which targets can match:

- **SDK endpoints** report every span they trace.
- **REST and WebSocket endpoints** report tool calls and retrievals through the `tool_calls` and `context` fields of their [response mapping](/docs/endpoints/response-mapping), or every span when the service sends its own traces. Map each tool call's `output` too: a tool call reported without one is judged with an empty result. A reported retrieval has no query of its own, so the turn's input is used as its query.

## Setting a target

A metric keeps its target in its `config`, as `config.target`. Send it when you create the metric, or change it later through the API or the MCP `update_metric` tool:

<CodeBlock filename="target.sh" language="bash">
{`curl -X PUT "$RHESIS_BASE_URL/metrics/$METRIC_ID" \\
  -H "Authorization: Bearer $RHESIS_API_KEY" \\
  -H "Content-Type: application/json" \\
  -d '{"config": {"target": {"on": "tool_call", "name": "issue_refund"}}}'`}
</CodeBlock>

The whole `config` is replaced, so send a built-in metric's own settings, such as the [Tool Call Trajectory](/docs/metrics/tool-calls) metric's `match`, along with the target.

A framework metric (DeepEval, Garak, Ragas) is read-only except its target. To point DeepEval answer relevancy at each retrieval, send `config` with the new target and its existing settings, and nothing else.

To list metrics by target, pass `target` with one or more choices: `GET /metrics/?target=turn,conversation`.

### In the app

The metric's page has a **Target** card, and the new metric form has the same target builder. Out of edit mode, the card shows the target, the full summary ("Judges …") and a **Show the spans it judges** link.

In the builder, **Start from** offers the presets as chips, plus **Custom spans** when the metric can take a span target. A per-span choice has an **Inside agent** field for `within`, and a preset also has a **Name** field. Custom spans list their conditions under **Judge each span where**. On a preset or a turn, the same list is optional and headed **Only … where**. Each condition row has a **Field**, an **Operator** and a **Value**. The field list holds the special fields and the attribute keys from the [attribute catalogue](#finding-keys-and-checking-a-target), grouped by span kind, and leaves out keys marked `unique`. The operators come from `GET /metrics/targets` and read as words, such as "is", "is not" and "is any of". The value field suggests the key's most common values. **The metric reads as input** and **And as output** set `read`; left empty, the metric reads the unit's own input and output. **The metric passes when** sets `aggregate` and `min_share`.

Under the builder, a summary box shows the target in the API's words. Beside it, **Matches in recent traces** previews the target on the last 50 traces of the project. It shows how many units match in how many traces, how many traces would be not applicable, and a few samples. When nothing matches, it says what the endpoint must report for the metric to run. The preview reruns shortly after you stop editing, once the target is complete, and the summary box follows it.

When a save returns `warnings`, such as a key no recent span carries, a notification shows them, and the Target card keeps them in an alert until you close it. The new metric form shows them in the notification after the metric is created.

On the metrics page, each card says what its metric judges under its name, such as "on each tool call named `issue_refund`", from `target_summary_short`. When the short form counts conditions instead of listing them, the tooltip holds the full summary. The target is a link to the Traces page's spans view, with the target itself as the filter, so the list shows exactly the spans the metric judges: each matching span, each turn's root span, or each trace's first root span for the run and the conversation. The link is `/traces?view=spans&target=…&from_metric=…`, and links saved before span targets still open. A chip above the list reads "Target:" with the target's summary and "from" the metric's name. Removing it clears the target filter and keeps the filters you added.

In the SDK, a judge takes `target` in its constructor, and `push()` and `pull()` carry it in the metric's `config`:

<CodeBlock filename="target.py" language="python">
{`from rhesis.sdk.metrics import NumericJudge

coherence = NumericJudge(
    name="conversation_coherence",
    evaluation_prompt="Rate the overall coherence of this conversation.",
    min_score=0,
    max_score=10,
    threshold=6,
    target="conversation",
)
coherence.push()`}
</CodeBlock>

A per-span target is a dict with `on` and, when needed, `name`, `within` and `aggregate`, as in the `targets.py` example below. To build a span target in Python, use `Target.spans(...)`; see [Metrics in the SDK](/sdk/metrics#span-targets).

## Trying a target locally

Pass `target` to `evaluate()` with a trace, or with the parts a trace is built from:

<CodeBlock filename="targets.py" language="python">
{`from rhesis.sdk.metrics import NumericJudge

judge = NumericJudge(
    name="refund_policy",
    evaluation_prompt="The refund matches the policy: at most one refund per order.",
    min_score=0,
    max_score=1,
    threshold=1,
)
result = judge.evaluate(
    input="Refund order 42",
    output="Refunded.",
    tool_calls=[{"name": "issue_refund", "arguments": {"order": 42}, "output": "ok"}],
    target={"on": "tool_call", "name": "issue_refund"},
)
print(result.details["reason"])`}
</CodeBlock>

A stored trace works the same way: `judge.evaluate(trace=Traces.pull(trace_id), target="retrieval")`.

## Migrating from metric scope

Targets replace the metric scope (`metric_scope`, a list of `Single-Turn` and `Multi-Turn`). The scope is gone from the API, the SDK (`MetricScope` and `MetricConfig.metric_scope`), the MCP tools, the app and Architect. A request that still sends `metric_scope`, such as one from an older SDK version, gets a 422 error. Upgrade the SDK and send `target` instead.

Stored metrics were given a target from their class and scope:

| Stored metric | Target |
| --- | --- |
| A conversational metric, or a metric scoped to Multi-Turn alone | `conversation` |
| A metric scoped to both, Tool Call Trajectory, or a code metric that reads only the trace | `run` |
| Every other metric | `turn` |

A metric scoped to both keeps doing what it did: `run` judges a single-turn test's one response, and a multi-turn test once, on its goal and whole transcript. This covers the built-in OWASP metrics, which look for attacks that build up over several turns. To judge each turn of a conversation on its own instead, set the target to `turn`.

A metric that can't read the whole trace got `turn` whatever its scope. That is one that reads only a turn's input and output (Garak detectors, the single-turn DeepEval metrics, code metrics that don't read the trace), or always compares with a reference answer (DeepEval's contextual precision and recall). A metric that was given `conversation` no longer requires a reference answer: it was scored against an empty one before.

Single-turn metrics used to be skipped on multi-turn tests. With a `turn` target they now run on every turn of a multi-turn test.
