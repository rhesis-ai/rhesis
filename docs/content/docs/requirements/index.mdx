# Requirements

Requirements are the expectations for how your LLM application should perform — response
quality, safety, brand voice, and so on. You attach metrics to a requirement to measure it,
and tag tests with a requirement so results roll up by expectation.

## Requirements and metrics

Rhesis uses a two-layer model: **requirements** state what you expect; **metrics** verify it.
One requirement can carry multiple metrics, so you can measure the same expectation from
different angles. See [Tests](/docs/tests) and [Test Results](/docs/test-results).

## Impact

Each requirement has an impact: what a failure costs, such as Safety, Privacy & security,
Legal & compliance, Financial, Reputation or Customer experience. If several apply, pick the
worst. Set it while creating or editing a requirement; **Manage impact options** next to the
field edits the list.

## Parent requirements

A parent groups related requirements, one level deep: a requirement with children can't have a
parent itself. Set it in the **Parent requirement** field. The requirement page links to its
parent and lists its children. Deleting a parent unlinks its children.

[Insights](/docs/results-overview) groups pass rates by requirement, impact or parent.

## Sources

Sources record where a requirement comes from: a policy, a regulation, a spec. On the
requirement page, **Add source** offers three options: upload a file, pick one from
[Knowledge](/docs/knowledge), or link a URL. Each source takes an optional note, such as the
section it refers to.

## Suggestions

**Suggestions** on the requirement page lists ways to make the requirement easier to test.

- **AI review**: your generation model reads the name and description and flags wording that
  can't be tested, such as "appropriately", or a requirement that covers two things. Where it
  can, it suggests a rewrite: apply it, edit it first, or dismiss it. Nothing changes until you
  apply. **Review again** reruns it after you edit.
- **Missing**: checks on the page, with no model involved: no source, no examples, no linked
  metric.

## Requirement tags

Requirement tags are optional labels for organizing and filtering requirements — use them when
several requirements share a feature area, risk theme, or team workflow. Add them while
creating or editing a requirement: type in the Tags field and press Enter, or pick an existing
tag from the suggestions. Tags are organization-scoped and reusable across requirements, and
the requirement grid can filter by them.

Requirement tags are distinct from a test's category and topic: tags organize requirement
definitions, while category and topic classify individual tests.
