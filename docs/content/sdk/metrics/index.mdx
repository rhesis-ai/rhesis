# Overview

The Rhesis SDK evaluates LLM applications with built-in metrics from several frameworks, custom metrics you define, and metrics managed on the platform.

## Metric types

- **[Single-turn metrics](/sdk/metrics/single-turn)** evaluate an individual exchange between a user input and a system output — RAG quality, response quality, safety, and custom checks.
- **[Conversational metrics](/sdk/metrics/conversational)** evaluate interactions across multiple turns — coherence, goal achievement, role adherence, knowledge retention, and tool usage.

## What a metric receives

Every metric judges what happened against what should have happened. Its `evaluate()` takes up to four arguments:

| Argument | What it is |
| --- | --- |
| `input` | What the endpoint was sent |
| `output` | What it answered |
| `trace` | Everything the endpoint did to answer, as a `rhesis.sdk.entities.Trace`: `trace.context`, `trace.tool_calls`, `trace.metadata`, and `trace.messages()` for a conversation |
| `expectations` | What should have happened: `response` (the reference answer), `goal`, `instructions`, `restrictions`, `contract`. A string is read as the reference answer |

Locally you rarely build a trace yourself. Pass the parts you have, and the SDK builds the trace from them:

<CodeBlock filename="evaluate.py" language="python">
{`# A judge with a reference answer
judge.evaluate(input="What is the capital of France?", output="Paris.", expectations="Paris")

# A RAG check: the documents the answer should rest on
faithfulness.evaluate(input=question, output=answer, context=documents)

# Tool calls and metadata the response reported
judge.evaluate(input=question, output=answer, tool_calls=calls, metadata={"latency_ms": 840})

# A conversation, as a list of messages or a ConversationHistory
goal_judge.evaluate(conversation=messages, expectations={"goal": "Book a flight to Paris"})`}
</CodeBlock>

In a test run, the platform passes the trace of what the endpoint did and the expectations from the test. On production traces there are no expectations.

## Targets

A metric's `target` says what it judges in a trace: each turn, the whole conversation, the whole run, or each span of one kind, such as every tool call. It also decides which tests the metric runs on. A `conversation` target never runs on single-turn tests, and every other target runs on both kinds.

Judges take `target` in their constructor. Without one, the metric gets its default: `turn` for `NumericJudge` and `CategoricalJudge`, `conversation` for `ConversationalJudge` and `GoalAchievementJudge`, and `run` for `ToolCallTrajectory`.

<CodeBlock filename="target.py" language="python">
{`from rhesis.sdk.metrics import NumericJudge

# Judge the conversation as a whole instead of each turn
metric = NumericJudge(
    name="conversation_clarity",
    evaluation_prompt="Rate how clear the assistant stays across the conversation.",
    min_score=0.0,
    max_score=10.0,
    threshold=7.0,
    target="conversation",
)`}
</CodeBlock>

`push()` and `pull()` carry the target in the metric's `config`. A per-span target is a dict with `on` and, when needed, `name`. See [Metric Targets](/docs/metrics/targets) for every choice, which tests each one runs on, and how to try a target locally with `evaluate(trace=..., target=...)`.

### Trace Evaluation

Any metric can also evaluate live production traces. Add it to a project's **Trace Metrics** in the project settings, and that project's traces are evaluated with it. A metric whose target is `conversation` runs on the whole conversation once it goes quiet; every other metric runs after each turn.

<Callout type="info">

For full details on how trace metrics evaluation works — including the two-phase pipeline, debounce timing, project configuration, and first-turn handling — see the [Trace Metrics](/docs/metrics/trace-metrics) documentation.

</Callout>

## Custom metrics

Beyond framework-provided metrics, Rhesis provides custom judges you define with a prompt and scoring rules:

- **`NumericJudge`**, **`CategoricalJudge`** — single-turn scoring and classification (see [Single-Turn Metrics](/sdk/metrics/single-turn))
- **`ConversationalJudge`**, **`GoalAchievementJudge`** — multi-turn evaluation (see [Conversational Metrics](/sdk/metrics/conversational))

## Generate and improve metrics with `MetricSynthesizer`

`MetricSynthesizer` creates metric definitions from natural-language instructions. Use it when
you know what you want to evaluate but want the SDK to draft the metric fields needed by the
platform.

The synthesizer returns a dictionary suitable for a `Metric` entity or the backend metric create
payload.

| Method | Input | Output |
| --- | --- | --- |
| `generate(prompt)` | Natural-language metric description | New metric fields such as `name`, `evaluation_prompt`, `score_type`, and thresholds |
| `improve(existing_metric, prompt)` | Current metric dictionary plus edit instructions | Updated metric fields for the same metric |

<CodeBlock filename="metric_synthesis.py" language="python">
{`from rhesis.sdk.entities import Metric
from rhesis.sdk.metrics import MetricSynthesizer

synthesizer = MetricSynthesizer(model="vertex_ai/gemini-2.0-flash")

metric_data = synthesizer.generate(
    "Create a numeric metric that scores whether a support answer is complete, "
    "accurate, and directly addresses the user question."
)

metric = Metric(**metric_data)
metric.push()

improved_data = synthesizer.improve(
    metric_data,
    "Make the threshold stricter and add evaluation steps for checking citations.",
)`}
</CodeBlock>

The generated fields follow the same metric schema used by custom judges:

| Field | Notes |
| --- | --- |
| `score_type` | Must be `numeric` or `categorical`. |
| `threshold_operator` | Used for numeric metrics; valid values include `=`, `<`, `>`, `<=`, `>=`, and `!=`. |
| `target` | `turn` or `conversation`, when the description says what the metric judges. Left out, the metric keeps its default. |

## Platform Integration

Metrics can be managed both in the platform and in the SDK. The SDK provides `push` and `pull` methods to synchronize metrics with the platform.

<CodeBlock filename="platform_integration.py" language="python">
{`# Push a metric to the platform
metric.push()

# Pull a metric from the platform
metric = NumericJudge.pull(name="response_clarity")

# Read what people have said about it
metric.get_annotations()`}
</CodeBlock>

`get_annotations` returns both kinds of judgement about the metric: where someone disagreed with it on a test result, and the metric tuning judgements about whether the metric itself is any good. See [Annotations](/sdk/entities/annotations).
