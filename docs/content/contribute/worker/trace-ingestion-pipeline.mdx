# Trace Ingestion Pipeline

This document explains how traces are processed after arriving via `POST /telemetry/traces` (SDK) or `POST /telemetry/v1/traces` (OTLP, Enterprise Edition), covering the full pipeline from storage through enrichment and metric evaluation.

## Pipeline Overview

Neither route writes to the database. The route validates the spans and queues them. A worker's `ingest_spans` task stores and enriches them in one transaction, then links them and queues their evaluation, the only follow-up job.

## Phase 1: Admission and Queueing

The routes share `routers/telemetry_intake.py`. Each request takes a per-process admission slot, reads its body under a size cap, and passes the queue-depth and per-organization rate checks (`services/telemetry/admission.py`). Parsing, OTLP translation and project checks run in a small thread pool, so the event loop never blocks and the route holds no database session. The spans become an `IngestJob` (`services/telemetry/ingest.py`), gzip-compressed inside the Celery message and split by size, queued as `ingest_spans` on the `trace-ingest` queue. The limits are the `TRACE_INGEST_*` settings; see [trace ingest limits](/self-hosting/environment-variables#trace-ingest-limits).

## Phase 2: Storage and Enrichment

The `ingest_spans` task (`jobs/telemetry/ingest.py`) runs `process_ingest_job`. It injects any pending mapped output into span attributes (for SDK endpoints where output arrives asynchronously) and runs the job's pre-store hooks (the OTLP route's hook re-files later conversation turns onto the conversation's first trace). Then `store_spans` (`services/telemetry/span_storage.py`) takes per-trace advisory locks, reads the trace's stored spans once, computes the trace's enrichment over stored and new spans, and inserts the new spans with it before a single commit. Spans already stored with the same trace and span id are skipped, so a resent batch is safe. A database failure retries the task with backoff; values the database refuses are logged and dropped.

Enrichment calculates three things from the trace's spans:

- **Token costs**: Uses LiteLLM's pricing database to calculate USD and EUR costs for each LLM invocation span. Looks for spans with `ai.operation.type = "llm.invoke"` and reads token counts from `ai.llm.tokens.input` / `ai.llm.tokens.output` plus the cached counts `ai.llm.tokens.cache_write` / `ai.llm.tokens.cache_read`. A span with no model, an unknown model or no tokens gets no cost rather than zero. See [Token Costs](/docs/tracing/costs).

- **Anomaly detection**: Flags slow spans (greater than 10 seconds), high token usage (greater than 10,000 tokens), and error spans.

- **Metadata extraction**: Collects unique models, tools, and operation types used across the trace.

The result is written to the `enriched_data` column of every span in the trace. If enrichment fails, the spans are stored without it.

## Phase 3: Linking

After the commit, the same task runs `process_stored_spans` (`services/telemetry/post_ingest.py`) on the rows it stored. It meters the spans and performs three types of linking:

1. **Test-result linking**: Associates trace spans with test results when spans carry test execution context attributes (`rhesis.test.test_run_id`, `rhesis.test.test_result_id`, etc.).

2. **Conversation-id linking**: Patches first-turn spans with conversation IDs that were not known at the time the span was stored. This happens when a stateful endpoint generates the conversation ID during invocation.

3. **Input file linking**: Attaches pending file records (images, documents) to their corresponding trace spans.

Each step commits on its own. A failed step is logged and rolled back, the later steps still run, and the ingest task is not retried, since the spans are already stored.

## Phase 4: Trace Metrics Evaluation

Last, `EnrichmentService.dispatch_for_spans` queues one `evaluate_turn_trace_metrics` task per root span on the `trace-eval` queue, and only when the project has trace metrics. The task applies the configured quality metrics (relevance, coherence, safety, etc.) to trace content. If the broker is unreachable, the evaluation is logged as skipped and not retried; the spans stay stored and enriched.

### Prerequisites for Evaluation

Evaluation requires all of the following:

1. **Celery workers consuming the `trace-eval` queue** -- evaluation runs there.

2. **Trace metrics enabled on the project** -- the project's `attributes.trace_metrics.enabled` must not be `false`.

3. **Trace metrics assigned to the project** -- `attributes.trace_metrics` must list at least one metric ID. Nothing is evaluated by default.

4. **Input/output attributes on the root span** -- the root span (a span with no `parent_span_id`) must include:
   - `rhesis.conversation.input` -- the user's input text
   - `rhesis.conversation.output` -- the system's response text

If any of these conditions are missing, evaluation is skipped silently with a log message.

### Multi-Turn (Conversation) Evaluation

For traces with a `conversation_id`, a second evaluation phase runs on a debounce timer. The `evaluate_conversation_trace_metrics` task:

1. Loads all root spans sharing the same `trace_id`, ordered by `start_time`.
2. Reconstructs the full conversation from `rhesis.conversation.input` / `rhesis.conversation.output` attributes across all turns.
3. Evaluates the project's Multi-Turn metrics against the full conversation history.
4. Derives a combined Pass/Fail status from both turn-level and conversation-level results.

## External Trace Ingestion

For deployments where the customer generates traces externally (e.g., with SDK tracing disabled), the same pipeline applies as long as the published spans meet the requirements.

### Required Span Attributes for Evaluation

When posting traces via `POST /telemetry/traces`, include these attributes on the root span to enable the full pipeline:

<CodeBlock language="json" isTerminal={false}>
{`{
  "spans": [
    {
      "trace_id": "abc123...",
      "span_id": "def456...",
      "parent_span_id": null,
      "project_id": "your-project-uuid",
      "span_name": "your.operation.name",
      "span_kind": "SERVER",
      "start_time": "2025-01-15T10:00:00Z",
      "end_time": "2025-01-15T10:00:02Z",
      "status_code": "OK",
      "attributes": {
        "rhesis.conversation.input": "What is the return policy?",
        "rhesis.conversation.output": "Our return policy allows..."
      }
    }
  ]
}`}
</CodeBlock>

| Attribute | Required For | Description |
|---|---|---|
| `rhesis.conversation.input` | Evaluation | The user's input text for this turn |
| `rhesis.conversation.output` | Evaluation | The system's response text for this turn |
| `ai.operation.type` | Cost calculation | Set to `ai.llm.invoke` for LLM spans |
| `ai.model.name` | Cost calculation | Model identifier (e.g., `gpt-4o`, `claude-3-sonnet`) |
| `ai.llm.tokens.input` | Cost calculation | Number of input tokens |
| `ai.llm.tokens.output` | Cost calculation | Number of output tokens |
| `conversation_id` | Multi-turn eval | Shared conversation identifier across turns |

### What Runs Without These Attributes

- **Enrichment** (Phase 2) always runs. Cost calculation skips spans that lack LLM-specific attributes; anomaly detection and metadata extraction still process all spans.
- **Evaluation** (Phase 4) requires `rhesis.conversation.input` and/or `rhesis.conversation.output`. Without them, evaluation returns early with status `no_io`.
