# Releasing

A Rhesis release is produced by three workflows in the repository's GitHub Actions tab, run in order. Each one is triggered by hand — nothing starts a release automatically.

The platform is the coordinated snapshot of the repository, tagged `v<version>` and marked as the latest GitHub release. The backend and the frontend ship as part of it: they take the platform's version and are covered by its tag, though each still keeps its own changelog. The SDK and Polyphemus are versioned independently and tagged `<component>-v<version>`.

<Steps>

### Set up the release config

Run `[Release] 1. Set up release config`.

Choose a bump — `patch`, `minor`, or `major` — for each component going out, and leave everything else on `none`. Bumping the platform also moves the backend and the frontend to the new version, so there is nothing to select for them. The workflow records the selection in `release_config.json` and commits it to `main`.

### Create the release branch

Run `[Release] 2. Create and deploy (stg)`.

This bumps the version files, generates the changelogs, creates a `release/*` branch, and opens a pull request against `main`. Pushing that branch triggers a staging deploy, so the release is on staging by the time the workflow finishes.

### Review on staging

Check the generated changelogs and the version changes in the pull request, and give the team time to test the release on staging.

<Callout type="warning">
  Hotfixes must be merged **into the release branch**, not into `main`. A fix that lands on `main`
  at this stage will not be part of the release.
</Callout>

### Deploy production and publish

Switch to the release branch and run `[Release] 3. Deploy and publish` from it. The jobs run in this order, and each one waits for the previous one:

1. Pins prd's ArgoCD Applications under `kubernetes/clusters/prd/` to this release's commit and syncs them. See [`kubernetes/README.md`](https://github.com/rhesis-ai/rhesis/blob/main/kubernetes/README.md#production-promotion-gate) for why prd config is pinned to a commit instead of the release branch name.
2. Copies the images staging ran into the production registry, unchanged, so production runs exactly what was tested.
3. Pins the `rhesis` chart to the release commit and sets the image tags in a single write, then waits for production to be healthy. Production never runs new images on the old chart or the other way round.
4. Creates and pushes the tags and creates a GitHub release for each component.
5. Squash-merges the release pull request from step 2 into `main` if every check on it passed, so the version bumps, changelogs and the new version in `docker-compose.ghcr.yml` and the chart land on `main`. It merges only after publishing: the tags are cut from the release branch, and merging deletes it.

If the deploy fails, nothing is tagged or published: fix it on the release branch and run the workflow again. If a check on the pull request failed, or it conflicts with `main`, the workflow leaves it open and fails its last job. The release is already live then: review the failure and merge the pull request by hand.

<Callout type="error">
  Run this workflow **on the release branch**. A run started from `main` is skipped by a branch
  guard and still reports success, so a release can look published when nothing was deployed or
  tagged.
</Callout>

To redeploy or roll back production later, run `[Build & Deploy] All for K8s` with environment `prd` from the commit you want.

</Steps>

## Verify the release

Publishing sets off several workflows that run independently of each other, so `[Release] 3. Deploy and publish` can succeed while one of them fails. After a release, confirm:

- **Tags** — `v<version>` for the platform, plus one `<component>-v<version>` per independently released component.
- **GitHub releases** — created from the changelog entries, with the platform release marked as latest.
- **PyPI** — `rhesis` and `rhesis-sdk` published. This is triggered by the `sdk-v*` tag, not by the publish workflow.
- **GHCR images** — built from the `v*` platform tag.
